## 2026-09-11 — 題材を計算 API に変更（承認済み）

Sprint 0〜4 でタスク管理 API を完成させたあと、学習の足場としては題材が大きすぎる
（用途が伝わりにくい / コア概念が埋もれる）という結論に至り、題材を
**四則演算をするだけの計算 API** に作り替えた。詳細と理由は [ADR 0006](adr/0006-pivot-to-calc-api.md)。

- 新エンドポイント: `POST /api/v1/calculations` の 1 本のみ
- 維持: スタック（Java 21 / Boot 4.0.8 / Maven）、層の一方向依存、package-by-feature、
  DTO=record、ProblemDetail、Spotless / Checkstyle / ArchUnit / CI / Docker / Render
- 撤去: 認証・認可、JPA / DB / Flyway、`User` / `Category` / `Task`、Testcontainers
- ルートパッケージ `com.example.taskapi` → `com.example.calc`
- 旧実装は git タグ `archive/task-api`（コミット `cfa1efd`）で保全

現行の仕様・受け入れ基準は [spec.md](spec.md)、決定の履歴は [adr/](adr/) を参照。

## 2026-09-25 — Model クラスと DB 連携を追加（承認済み）

利用者から「REST API の基本が詰まった仕様にしたい。Model クラスや DB 連携まで含めたい」という
要望が出た。題材（計算 API）は維持したまま、**計算履歴を DB に永続化するリソース**に拡張する。
詳細と理由は [ADR 0007](adr/0007-reintroduce-model-and-database.md)。

- リソース設計: 計算履歴を永続化（`Calculation` エンティティ 1 つ・テーブル 1 つ）
- DB: **PostgreSQL 17 + Docker Compose**（テストは H2 インメモリなので `./mvnw verify` は Docker 不要）
- REST: 一覧 / 取得 / 作成（201 + `Location`）/ 全置換（PUT）/ 部分更新（PATCH）/ 削除（204）＋ 404
- 追加で学ぶもの: `@Entity`・Repository 層・`@Transactional`・Entity ↔ DTO 変換（手書き Mapper）
- 今回のスコープ外: ページング、Flyway、1 対多リレーション、認証（[spec.md](spec.md) §6「今後の候補」）
- ADR 0006 の「永続化なし・Docker 不要」は撤回。「題材は計算 API」「認証なし」の判断は維持

不採用案（H2 だけで完結 / タグを足して 1 対多 / 別リソース追加 / Flyway 同時導入 /
ページング同時導入 / PUT で upsert）は ADR 0007 の表に記載。

## 2026-09-26 — REST API としての仕上げ（承認済み）

利用者から「REST API の最新のポピュラーな実装を、徹底的に、それでいて必要最低限に」という要望が出た。
全体を見直し、実際に HTTP で叩いて見つかった不具合 3 件と、欠けていた定番 1 件を入れる。
詳細と理由は [ADR 0008](adr/0008-rest-api-finishing.md)。

- 不具合 1: 結果が `NUMERIC(38,10)` に収まらない計算（28 桁 + 28 桁など）が **500** → **422** にする
- 不具合 2: 想定外の例外が Spring Boot 既定の JSON で返る（不変条件 #4 違反）→ **500 も ProblemDetail**
- 不具合 3: PATCH に `{}` を送るとメモが消える → **JSON Merge Patch（RFC 7396）の意味**
  （省略 = 変更しない / `null` = 消す）。`application/merge-patch+json` も受け付ける
- 追加: **一覧のページング**（`?page=&size=`、Spring Data の `PagedModel`）。ADR 0007 の「ページングは入れない」を覆す。
  一覧のレスポンスが配列 → オブジェクトに変わる破壊的変更
- 入れないもの: 楽観ロック（`@Version` + ETag / `If-Match`）、クライアント指定のソート、Idempotency-Key、
  認証、Spring Framework 7 のネイティブ API バージョニング（パスの `/v1` を維持）

## 2026-09-26 — 学習教材（教科書 ＆ 問題集アプリ）を作る（承認済み）

利用者から「このAPIを題材に、何度も復習できる教科書 ＆ 問題集にしたい」という要望が出た。
詳細と理由は [ADR 0009](adr/0009-learning-app.md)。

- 形式: **HTML アプリ 1 つ**（`docs/learning/index.html` ＋ 章ごとの内容ファイル）。リポジトリにコミットする
- 章の型: 地図 → **実物を開いて確認**（必須）→ 動かして観察 → 設計判断（ADR）→ AI 駆動の観点 → 4 択
- ゲート: 章ごとに 15〜20 問のプールから**ランダムに 10 問、9 問以上で次の章が解放**。選択肢はシャッフル
- 読者: **IT の前提知識ゼロ**。ただし解説は実装の細部ではなく**アーキテクチャと設計の大局**に絞る（AI 駆動開発が前提）
- 実装と紐づけられる箇所は必ずリンク（VS Code で開く ＋ GitHub で見る）。リンク切れは JUnit で検査する
- 実装に無い必須知識は**座学の章**として実例で解説する: 認証・認可 / API セキュリティ / DB の発展（Flyway・N+1・インデックス）/
  外部 API 連携 / 可観測性。冪等性・同時更新は入れない
- 全 26 章（7 部）。既存の `textbook.md` / `curriculum.md`（Sprint 5 時点で古い）は新教材が揃った時点で削除
- 進め方: Sprint 8 で骨格 ＋ 第 1 部（1〜4 章）を作り、使ってもらってから残りを部ごとに作る

## 2026-09-26 — 学習アプリに「アジャイル・スクラム編」を足す（承認済み・Sprint 10 で実装）

利用者から「API 編の学習 HTML を踏襲しつつ、アジャイル開発・スクラムの知識も学べる教材を作りたい」という
要望が出た。壁打ちで以下に合意した。API 編（Sprint 9）を先に完了させてから着手した。
決定は [ADR 0010](adr/0010-agile-course.md)（ADR 0009 の「26 章・7 部」を拡張する）。

- 構造: **同じ `index.html` で「コース」を切り替える**（API 編 / アジャイル編）。outline と進捗の保存キーをコースごとに持ち、
  図の部品・問題エンジン・リンク検査は共有する（不採用: 第 8 部以降として同じ outline に追加 ＝ 解放が直列で
  並行して学べない / HTML を複製 ＝ 二重保守）
- 目的: **現場でスクラムを回せること**。資格対策（スクラムガイドの文言暗記など）はしない
- 読者: **ウォーターフォールの経験がある**。全章に「ウォーターフォールではこうだった」欄（章の型に `wf:` を追加）を置き、
  既知のものとの対比で学ぶ（要件定義書 ↔ プロダクトバックログ、WBS ↔ スプリントバックログ、進捗会議 ↔ デイリー、検収 ↔ レビュー＋DoD）
- 範囲: **アジャイル・スクラムの基本が伝わる最小限**。「知らないとスクラムチームで仕事が回らないか」を基準に削る
- 実物: このリポジトリの `docs/`（spec.md の受け入れ基準と「今後の候補」、CLAUDE.md の DoD、`sprint-N` タグ、
  `learning/sprint-N.md`、ADR 0006 の方向転換）を実例にリンクする。**このリポジトリの Sprint は厳密なスクラムではない**
  （期間で区切らない・利害関係者がいない・一人＋AI）ことも教材として正直に扱う
- 問題: API 編と同じく 1 章 15 問以上、状況判断型を中心にする

章立て（4 部・9 章）:

| 部 | 章 | 内容 |
|---|---|---|
| 1 アジャイルとは | 1 | なぜアジャイルか: ウォーターフォールとの違い（不確実性 → スコープを動かす、小さく出して学ぶ）、アジャイル宣言の 4 つの価値 |
| 2 スクラムの仕組み | 2 | 全体像: スプリントというループと、透明性・検査・適応 |
| | 3 | 3 つの役割: PO・スクラムマスター・開発者（誰が何を決めるか） |
| | 4 | 5 つのイベント: 目的・入力・出力（利害関係者との関わりはレビューで扱う） |
| | 5 | 3 つの作成物と確約: プロダクトバックログ／プロダクトゴール、スプリントバックログ／スプリントゴール、インクリメント／DoD |
| 3 バックログを回す | 6 | プロダクトバックログの育て方: ユーザーストーリー、縦に切る分割、受け入れ基準、リファインメント、価値の順に並べる |
| | 7 | 見積もりと計画: 相対見積もり、ベロシティ、バーンダウン（目標にしない等の誤用の注意込み） |
| 4 現場で | 8 | よくある失敗と、ウォーターフォールの組織で始めるとき（契約: 請負と準委任を 1 節） |
| | 9 | このリポジトリを振り返る ＋ まとめ |

入れないもの（基本の範囲外）: 12 の原則の個別解説（一覧のみ）、カンバン・WIP 制限（名前だけ触れる）、
XP・TDD・CI の章（API 編 20・21・23 章へリンク）、ADR・文書の章、MVP・MoSCoW 等の優先順位手法、
複数チーム（LeSS・Nexus・SAFe）、DEEP・INVEST 等の略語の暗記、プランニングポーカーの手順、資格対策
