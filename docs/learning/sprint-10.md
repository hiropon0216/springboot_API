# Sprint 10 学習ノート — 保存データを壊さずにコースを足す・自分たちを教材にする

対象: 2026-09-26 / 決定は [ADR 0010](../adr/0010-agile-course.md)

この Sprint では、学習アプリに 2 つ目のコース「アジャイル・スクラム編」を足した。
学んだのは「すでに使われている仕組みに、利用者のデータを壊さずに次元を 1 つ足す」ことと、
「自分たちの進め方を、正直に教材にする」こと。

## 1. 概念の核心

### 1.1 既存のデータの形を変えずに、住み分ける

コースを足すとき、保存データを `{ api: {…}, agile: {…} }` のように作り直すと、Sprint 9 までの進捗と書き出したファイルが読めなくなる。
そこで **API 編の鍵は章番号のまま**、アジャイル編だけ `agile:3` のように前置きを付けた。

| 選択肢 | 既存データ | 読み替え処理 |
|---|---|---|
| 形を作り直す | 読めなくなる | 必要（移行コードとそのテスト）|
| 別の保存場所に分ける | 読める | 不要。ただし書き出し・読み込みが 2 つになる |
| **同じ形の中で鍵を住み分ける（採用）** | **読める** | **不要** |

記録（`attempts`）にも `course` を足したが、**無い場合は API 編として扱う**ので古い記録もそのまま表示できる。
URL も同じ考え方で、API 編の `#ch/3` は変えず、アジャイル編だけ `#agile/ch/3` にした（ブックマークが壊れない）。

### 1.2 関数に「どのコースか」を通す

もともと `status(no)` のように章番号だけで動いていた関数に、`status(c, no)` とコースを通した。
大きな変更だが、やったことは機械的：**グローバルに 1 つだった前提（目次・章の置き場所）を引数にする**。
変更のあとに、古い呼び方（`status(no)` や `Calc.chapters[no]`）が残っていないかを grep で確かめた。

### 1.3 「実物」はコードでなくてもよい

REST API 編の「実物」はコードだったが、アジャイル編の実物は `docs/`（spec・DoD・progress・ADR）と git のタグ。
同じ `code()` とリンク検査がそのまま使えた。教材が文書を指していても、**文書が変わればテストが赤くなる**。

### 1.4 自分たちの「守れていないこと」を教材にする

9 章で、このリポジトリがスクラムとして守れていないことを実物で確かめて書いた。

- spec.md の受け入れ基準のチェック欄は 1 つも付いていない（`[x]` が 0 件）
- DoD に「git tag sprint-N」があるのに、sprint-2〜6 が無い
- CLAUDE.md の表にある `docs/feedback/` が存在しない
- Sprint 7・8・9 は同じ日に終わった（タイムボックスが無い）

**書いた以上、このスプリントの受け入れ基準には、確かめたものにチェックを付けた**。教材で言っていることと、自分たちのやり方を合わせる。

## 2. つまずいたところ

- **検査スクリプトが HTML コメントの中の例を読んだ**。`index.html` の先頭のコメントに `<script src="chapters/…/chNN.js">` と書いていたので、
  簡易 DOM の検査がそれを読み込もうとして落ちた。コメントを取り除いてから `<script>` を拾うようにした（`LearningLinksTest` は `…` を含むので一致しない）
- **要望の文言を言い換えて「引用」していた**。5 章で ADR 0008 の要望を記憶で書いたら、実際の文言と違っていた。引用するなら実物を開いて写す
- **記憶で書いたスクラムの説明が、原文と少しずつ違った**。総点検でスクラムガイド 2020 年版の原文と突き合わせたら、
  「レビューの出力は見直されたプロダクトバックログ」（原文は「調整されることもある」）、「3 つの質問は 2020 年版で必須でなくなった」
  （もともと例にすぎない）など、言い切りすぎが見つかった。**よく知っているつもりの分野ほど、一次情報で確かめる**
- **正解だけ長い選択肢**。状況判断の問題を書くと、正解の選択肢だけ説明が長くなりがち。検査スクリプトで長さの比を測り、誤りの選択肢も「現場でありがちな判断」として同じくらい具体的に書き直した

## 3. 復習問（答えは下）

1. コースを足すとき、保存データの形を作り直さなかった理由は？
2. アジャイル編の記録と、Sprint 9 までの記録はどう見分けている？
3. アジャイル編の「実物」へのリンクが壊れたら、どうやって気づく？
4. 「選択肢の正解だけが長い」と、何が困る？
5. 9 章で「守れていないこと」を書いたあと、このスプリントで自分たちのやり方に反映したことは？

### 答え

1. 作り直すと、利用者の Sprint 9 までの進捗と書き出したファイルが読めなくなる。API 編の鍵はそのままにし、アジャイル編だけ `agile:` を付けて住み分けた。
2. 記録に `course` を付けた。`course` が無い記録は Sprint 9 までのものなので、API 編として扱う。
3. `LearningLinksTest` が `chapters/agile/` も検査するので、`./mvnw verify`（と CI）が赤くなる。実際に 1 つ壊して確かめた。
4. 本文を理解していなくても、長い選択肢を選べば当たってしまう。理解の確認にならない。
5. このスプリントの受け入れ基準のうち、確かめたものにチェックを付けた（確かめていない 390px 幅は付けていない）。
